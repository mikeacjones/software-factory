# Architecture

The software factory takes beads from a project's backlog and turns each one into a merged pull request, without anyone watching. This page states the decisions already made. Terms in *italics* are defined in the [glossary](glossary.md). [how-it-works.md](how-it-works.md) draws the same as flow and sequence diagrams.

## Who owns what

- **Beads own what the work is.** The factory reads work from each *project*'s bead database and never keeps its own copy of a *bead*.
- **Redis owns how the factory is processing it.** *Unit* records, *run* records, leases, pauses, questions and the audit log live in Redis. Jobs, results and events travel on Redis Streams.
- **Git and GitHub own code and CI.** A branch, a pull request and its checks are read from git and GitHub each time, not remembered.

The driver is level-triggered. Every *tick* it rebuilds what it believes from Redis, beads, git and GitHub, so a lost message or a change the owner made by hand cannot leave it stuck.

## Agents propose and code acts

An agent returns a typed *result*. Code checks it and code carries out every action: committing, pushing, opening a pull request, landing, closing a bead, posting to Slack.

Agents never talk to each other. A *job* message goes in and a *result* message comes out. An agent *step* has no memory beyond the *session* its *flow* tells it to continue.

A project's *flow* decides which *steps* run, in what order and on which model. Failure handling, the preconditions for landing and the invariants are code. No flow can change them.

## No agent is sandboxed

Owner's decision, 2026-11-14. Every agent runs in bypass mode as the owner's account on this Mac. There are no separate macOS accounts, no deny rules and no per-agent restrictions: the machine is the sandbox. Three things follow.

1. **Output is checked after the run**, since nothing restricts an agent while it runs. Each step's changes are compared with the path scopes its flow allows, and its typed result is validated against the diff and the bead. A path no step may change, once changed, parks the unit after every step until it is as it was before; the step that puts it back is not stopped for changing it. Whether a path is forbidden is asked of the config read when the unit runs, at every step: a trespass on a path the owner has since stopped forbidding is dropped, with a `trespass.dropped` event, and parks nothing.
2. **Files the factory depends on are checked by content hash.** Config, flows and *artifacts* can all be edited by an agent, so a change is detected, never trusted. A unit runs on a pinned copy of its flow.
3. **What the machine can reach is set by the credentials stored on it**, so those are kept narrow. The GitHub credential is a fine-grained token limited to the repositories the factory works on.

## The first cut

The first milestone walks one bead to a pull request by hand: `factory run <project> <bead>`. It is a thin slice through the crates above, not a separate program. What it leaves out is listed here so nobody mistakes it for the whole design.

- **No Redis.** A unit's state is one JSON file and its audit log one JSONL file, both under the state directory. The driver walks a single unit in the foreground; there are no ticks, slots or leases.
- **No stall rules.** A run is judged by its exit, its output stream and a wall-clock cap.
- **Accounts are balanced by their windows.** Capacity left in a window when it resets is lost, so each run uses the account whose week resets soonest, and between accounts whose weeks end together, the one whose five-hour session resets soonest. An account at its session or weekly limit is left until that window resets, a limit on one model leaves the account usable for others, and a run refused at a limit continues its session under another account. When every account is at a limit the step, or the director, waits for the earliest reset. An account's token for runs can be named in a file of variables (`token_env_file` with `token_env`), which is then its only source: the Keychain, the factory's environment and the CLI's own login are not looked at, and an empty value is an error. The factory's accounts are kept that way, in the file the owner's shell reads its own `claude` and `claude2` tokens from, so that an account is the same subscription in the factory as in the shell and does not change when someone logs in to the CLI. Nothing is polled: every run's rate-limit event reports both windows, and an account the factory has not heard from for half an hour is asked about once, through the subscription's usage endpoint, with no model call. That read is an extra, for an account that has a full login kept in the Keychain; a run token cannot make it. It is also the only report of a model's own weekly window, such as Fable's: the factory keeps it beside the account's two windows and the dashboard shows it with the time it was read, since a busy account's runs keep it from being asked again. A login nothing else keeps fresh is refreshed by the factory when it is about to expire. The login Claude Code itself uses is refreshed too, since Claude Code only does so while it runs under it, and it is done the way Claude Code does it: the factory takes the lock Claude Code keeps in its configuration directory, reads the stored login again, refreshes only if it is still due, and writes it back to the same Keychain item, so neither spends a refresh token the other still holds. The first time a login is used the factory asks whose it is and keeps the answer; a login that later belongs to another account is refused, because its windows would be another subscription's, until the owner accepts it with `factory accounts pin`. An account whose open weekly window is reported to end at a different time has had its login or token changed underneath it, and two accounts whose logins or weekly windows are the same are one subscription listed twice: `factory accounts` says so in both cases.
- **Landing is one unit at a time.** After the pull request is opened the factory watches its checks by polling, with no model involved. A failed check ends the wait once the checks still running have finished, or after `ci_red_wait_secs`: every failure and its log goes back to the builder's session together, and the fix goes through every step again. Where the project sets `ci_reruns`, the failed jobs are first run again on the same commit, that many times, by code: jobs that then pass were a flake, and no builder is sent. When every required check has passed, the factory merges the pull request, confirms the merge commit is on the default branch, closes the bead and removes the worktree, without asking any agent. A pull request that conflicts with the default branch, or whose head is not the commit the factory published, parks the unit. There is no landing queue yet, because there is only one unit.
- **Steps run one at a time, except a group of commands.** A step of kind `commands` names several of the project's commands. The driver starts them all at once in the unit's worktree, waits for every one to end, and only then decides: the step passes when each passed, and fails when any failed, with every failure in what the builder is given, not only the first. One that parks (the host's fault, or the same failure as before the last fix) parks the group. Each command is still judged as a step of its own would be, with its own output file, triage and `when_changed`. A command that changes the worktree as it runs is marked `edits` in the project, and in a group it runs first and alone, so that no other command reads a file it is in the middle of writing. A command that produces an artifact, a report-only command and one that must fail stay steps of their own. The group is one activity to the engine, so the unit's record is written by one process and a worker that dies runs the group again whole. Agents and actions still run one at a time.

The first flow, `build-break-review`, has four roles. The **builder** implements the bead, and its session is continued for every fix. The **tester** is adversarial: it gets a scratch worktree at the checkpoint and tries to break the change by running it, and every finding must carry a reproduction it ran. The **reviewer** reads the change. The **publisher** continues the builder's session to write the commit message and pull-request text. Slack is one channel per project and one thread per run; the owner steers by replying in the thread.

A flow can also carry reports. A command step may say it *produces* a named artifact, such as a directory of scanner output, and an agent step may say it *needs* one. The factory gives the command a directory outside the worktree, and briefs each step that needs the artifact with where it is and what its index says. The validator refuses a flow in which, on some path, a step would be given reports that are missing or were written before the code last changed.

## How a finding and a fix are proved

The adversarial tester does not get to assert a bug, and the builder does not get to assert a fix. Both are settled by a test that code runs.

- **A finding is a failing test.** For each critical or major finding the tester leaves a regression test in the project's own suite and names the command that runs it. The factory runs that command in the tester's worktree before accepting the finding: if it passes, or cannot run, the finding goes back to the tester. What the tester leaves may only add lines.
- **The tests join the branch.** The factory commits them to the unit's branch, failing. A later round of testing starts from code that already holds them, and a fresh tester or reviewer is told what earlier rounds found, since it shares no session with them.
- **A fix is that test passing.** Before a builder's result is accepted, the factory runs every regression test the unit has gathered, and checks that none has disappeared from the code. While one fails the result goes back to the same session.
- **From the second break on, the approach changes.** The fix is told to stop patching the reported case: write down the invariant, list the orderings and states, check each. A flow can also raise a step's effort by round.

Two further checks need no model. A command step, or a command in a group, can be limited to changes that touch given path scopes, which is how the optimized test run joins a bead's pipeline only when the runtime changed. A report-producing command can name results that must never pass (`fail_when`); the rest of the report stays advisory. And when a later round of changes removes lines that look like tests or assertions, the reviewer is pointed at them.

A failed check is looked into before a builder is sent (*triage*, epic sf-0kw), by code and in this order. Output a project's command names as the host's fault (`could_not_run_when`, `could_not_run_exit`: a broken download, Docker not running) parks the step, as a command that could not start does. With `triage.rerun` it is run once more on the change, and a pass there passes the step as a flake, recorded. With `triage.base` it is run on a copy of the worktree (a clone, build caches included) with every file the change touched put back as at the unit's base: a failure there too, on the same failure lines, is not the change's and parks the step with both results; a pass there sends the builder, told so. Last, a failure with the same signature as the step's previous one (the lines `failure_lines` pick out, or the last lines, with numbers, hex and paths taken out) parks instead of sending another fix round; a unit moved by hand, or whose base moves, starts with none remembered. A sub-goal whose ship parked before its pull request was opened, shipped again, goes on from the start of the ship flow and not from where it stopped, so the default branch is taken in again and every check runs on what will land; no builder is sent back to a failure that may have been dealt with on the default branch. A command that reaches its time limit is sent SIGTERM and has `stop_grace_secs` (30 unless set) to stop what it started and print what it has before SIGKILL, so its output and its cleanup survive a hang. Owner's decision, 2026-11-16, after a test server release hung a ship's Linux run for an hour and sent a builder after it.

A failure that is not the change's is still somebody's, and the factory does not hand it to the owner (epic sf-se3). Four rules, all carried out by code:

- **CI is run again by code.** With `ci_reruns` set in a project's `[github]` table, a pull request's failed jobs are run again on the same commit before a builder is sent: only the jobs that failed (`gh run rerun --failed`), never the whole run, and only once no job of it is still running. The unit's record keeps how often, so a watch taken up after a restart does not start counting again. If they fail each time, the builder is told so. A builder that finds the failure is not the branch's returns `already_done`; when the flow then reaches the watch again with the commit unchanged, the old failure is not news and the jobs are run once more. The flow's own limits on those routes are what ends it, by parking.
- **A flake is a finding.** A check that failed and passed on one commit, a command of the project (`command.flaky`) or the jobs of CI (`ci.flaky`), is kept in the unit's record with the commit, the failing lines and where the output is. When the pipeline ends it is among the findings its director or foreman rules on, marked `flake`, and the roles say what to do: add it to the bead that covers it, or file a bug, and put the fix ahead of the plan when it has stopped a pull request. The bug is to be fixed at its cause. The director and the foreman write the bead to ask for the cause and to rule out a retry, a longer time limit, or a test skipped, loosened or marked flaky; the builder is told the same; and the reviewer sends back a change that only lives with the defect. Running a check again keeps other work moving while the defect stands, and is never its fix. The measures of a scheduled run count both kinds.
- **A ship's commits are checked while their author is there.** A sub-goal's commits are published as they are, so the project's `publish_checks` are run on the branch before a fix on it is accepted. What they refuse goes back to the same builder session, which rewords the commit it made. If the publish step still meets a commit the checks refuse, the ship flow sends it to the builder, since no text the publisher writes changes a commit of a ship.
- **The director may change what its goal filed.** `edit_beads = "own"` in a goal definition's `[permissions]` carries out a change to a bead that the goal's own agents filed, or that a maintenance run filed for the goal to build, and puts a change to any other bead to the owner. Which beads those are is read from the goal's log each time the director is woken.

Owner's decision, 2026-11-17, after a test that hangs now and then on the default branch left a goal waiting a night for the owner to run CI again, to amend a commit message, and to approve the priority of a bug the goal itself had filed.

A classifier may be asked what kind of failure a failed check shows, and what it says is recorded and nothing more (`factory-checks/src/judge.rs`, owner's decision, 2026-11-17). With a `[judge]` table in `factory.toml`, the lines of a failed command, and of the first log of a red CI, that say what failed are sent once to TypeSafe's Jev, a model that answers a question with fixed answers and a probability for each: `host`, `timeout`, `crash`, `compile`, `policy` or `assertion`. The reading goes into the unit's log as `failure.judged` with its confidence and the time it took, before the checks above run, and none of them reads it. A key that is missing, a refusal or an answer later than `timeout_secs` is logged as `failure.judge_failed` and holds nothing up. Without the table nothing leaves the machine. It is a shadow so that its readings can be set against what the rerun and the base run then found, on this factory's own failures, before any route is given to it: on seven of them it named the kind right wherever the answer was clear, in about 130 ms each, while its guess at whether a failure was a flake put a real flake below a deterministic failure, and its guess at whether the test or the code was wrong came back unsure, so neither is asked. It can be argued with: one sentence added to a finding moved all 57 serious ones it was shown to not serious. So it is given a check's output and never an agent's account of its own work, and it never gates a landing.

How the factory ran over a period is worked out by code from its records (`factory report`, `factory-driver/src/report.rs`): units started, landed, absorbed and parked, cost per bead closed, fix rounds, time per step, why units parked, how often each triage outcome fired, checks that ran to their limit, how long the owner was waited on, and the classes of defect testers proved. It reads the state directory and changes nothing. It is what a review of the factory reads, so that the figures do not come from a model judging its own work (epic sf-yd3).

## Goals

A pipeline takes one bead to its landing. A *goal* sits above pipelines: an objective and a stop condition on a *project*, the *director* that runs it, the *flow* its beads go through and how many pipelines it may have at once. How goals of a kind run is a file, `goals/<project>/<id>.toml`; the objective itself comes from the owner.

- **It starts as a conversation.** The owner's top-level message in the project's channel opens the goal, and that message's thread is the goal's. The director talks with the owner in one session until it can propose a charter: objective, stop condition, plan, and any bead changes the owner agreed to. Nothing is written or run until the owner presses Start.
- **It runs on events.** A pipeline ended, the owner wrote in the thread, the owner answered a request: each wakes the director, in a fresh session briefed by code with the charter, what happened, the tracker, its own journal for the goal and the project's memory. Between events no model runs. The brief holds the newest four entries of the journal in full and names the file with the rest (`recent_journal`): on the Zig project a director's brief had grown to 390,000 characters by its 47th wake, 300,000 of them every entry it had written, read again on each turn. An entry therefore carries forward what still matters, and the roles say so. A foreman's journal is shown the same way. Owner's decision, 2026-11-17.
- **The director decides and code acts.** Its result is a list of decisions: start a bead's pipeline, file a bead with a type, a priority and whether it is deferred, change a bead that exists, ask the owner, propose completion. Code refuses a start on a bead that is not launchable or past the cap, completion without evidence, and any result that would leave the goal with nothing to move it. What the director may do alone is the goal definition's `[permissions]`: by default it files new beads freely and a change to an existing bead is put to the owner. With `edit_beads = "own"` a change to a bead the goal itself filed is carried out at once, and only a change to someone else's bead is put to the owner. With `director_decides = true` on the project, or on one goal definition to override it, the owner has left decisions to the director: a result that only asks the owner and leaves nothing running is refused, so the director goes with its own recommendation and says what it chose, and its `complete` ends the goal with no Accept. The owner still presses Start on each charter. Which model a director wake runs on is decided by code from the goal's record, never by a model (`wake_route` in `factory-driver/src/goal.rs`, owner's decision, 2026-11-18): the owner, a new goal, a landed sub-goal and a design waiting for a ruling go to the director's own model; a foreman's ready report on a sub-goal whose planned beads are all absorbed, with nothing added to it, running in it, or waiting on the owner or a red default branch, goes to the definition's `routes.ship`, which may only ship or hand up; anything else (an escalation, a failed pipeline or ship, a note) goes to `routes.settle`, which may start, continue, ship and talk to the foreman and the executive. A lighter wake that wants any other decision, or says `hand_up`, is run again on the director's own model in the same turn, told why. A tier with `fallback_model` runs on it when every account is at its limit for its own model, logged as `<who>.fell_back`, rather than wait; a designer may not have one, since its design binds every builder of its sub-goal. On a settle wake, where the record alone does not say how much the wake needs, the classifier is asked in shadow what the director has to decide (`replan`, `rule` or `proceed`, heaviest first), from facts code writes and never an agent's words; the reading is logged as `wake.judged` beside `wake.decided`, the same answers taken from what the director did, and routes nothing until the two have been compared. The classifier's answers are sent in the order they are listed, written out by hand, since a JSON map would sort them by name.
- **A goal is worked in sub-goals.** When the goal definition names a `ship_flow`, the director opens a *sub-goal* for each part that should land as one pull request, one at a time. A sub-goal has a branch and worktree of its own. Each of its beads runs the light pipeline (`flow`): it branches from the sub-goal's tip, is built, checked quickly, adversarially tested and reviewed, and ends with the `absorb` action, which adds it to the sub-goal's branch as one commit. Nothing is pushed and the bead stays open, so a bead blocked only by beads its sub-goal has absorbed may be started. When the director ships the sub-goal, the heavy pipeline (`ship_flow`) runs once on that branch: the whole repository's checks, a review of the beads together, one pull request holding the commits as they are, CI, and a squash onto the default branch. Landing closes every bead of the sub-goal. A failure while shipping has no builder session to return to, so the ship pipeline's fix step is a fresh builder on the sub-goal's branch. Without a `ship_flow`, every bead is its own pull request.
- **A sub-goal can have a foreman.** When the goal definition has a `[foreman]` table, the agents that run a goal are two *tiers* of one mechanism: an inbox of events from the level below, a fresh session at every wake, a journal of its own, and decisions that code checks. The director opens a sub-goal, naming its beads, and that hands it to the sub-goal's *foreman*. The foreman is woken when the sub-goal opens, when one of its pipelines ends and when the director writes to it. It starts the sub-goal's beads, rules on what their testers and reviewers left unfixed, and may file a bead to run in the same sub-goal. It may start only beads the director planned or that it filed to run there. It never leaves the sub-goal idle: after each of its decisions a pipeline is running, or it has told the director `ready` or `escalate`. The director is then woken only by a foreman's report, by shipping ending and by the owner; it answers with `tell_foreman`, ships, or asks the owner, and code cuts off an exchange between the two that starts nothing: after six messages with no pipeline started or continued, `tell_foreman` is refused and the director must ship or ask the owner. The owner's reply in the goal's thread lifts that cut on every open sub-goal, since the owner has no way to write to a foreman but through the director. A foreman that cannot be run five times in a row hands its sub-goal to the director. The foreman reads a checkout of the sub-goal's branch, apart from the branch's own worktree. Each tier has `slots`, the most work it may have running below it at once: a limit, never a target.
- **A pipeline that stops is continued, not restarted.** A bead's pipeline that parks or fails keeps its unit: worktree, branch, commits and sessions. Whoever runs the sub-goal's beads, its foreman or else the director, is told it stopped and where its record is, and may `continue` it: from a step of the bead pipeline it names, with a note that the step reads as feedback. The unit is put on the pipeline as it is now and everything after that step runs as usual. Continuing does not give the unit a new allowance on its bounded routes: a used-up route out of the step it goes on from gets one more use, so that going on is not futile, and every other count stands. A pipeline that parked because its tester broke it too often therefore has its fix made and tested once more, and the next break comes straight back to whoever continued it. A continue may carry a *ruling*: a decision about the bead, such as what is out of scope or how a question of design is settled, that is kept in the unit and shown to every agent step from then on. A note reaches only the step continued from; a ruling is how the tester and the reviewer come to know what was decided. A start on a bead whose pipeline stopped is refused. A pipeline may be continued three times before it has to go up a level, and the director writing to the foreman opens that again. A flow sends every break by the tester back to the builder and parks after three fixes: a break commits a failing test to the branch, so the validator treats it as a change to the code and refuses a flow that would pass it on to a step whose reports describe the code before it. On restart, an open sub-goal of a goal whose definition has gained a foreman is given one, which is told it takes over part-way; since a goal reads the definition it is pinned to, that is a goal whose record holds no pin.
- **Beads of a sub-goal are built side by side unless one builds on another.** A sub-goal's design says for each bead which beads of the sub-goal it comes *after*: the ones whose type, signature or file layout it uses. Code refuses a design whose edges name a bead outside the sub-goal, the bead itself, or a bead the order lists later, so there is no circle. A foreman with more than one slot may start any beads together whose design puts nothing between them, whatever files they change and whether or not they declare *paths*; a bead whose design names one not yet absorbed is refused. In a sub-goal with no design, and in one whose design was written before designs said this, nobody has said what builds on what, and the old rule stands: beads run together only when each has declared paths and no two overlap (a directory holds everything under it). Each bead is built in its own worktree from the sub-goal's tip as it was. Absorbing is one at a time. When a unit comes to be absorbed and the tip has moved, the `absorb` action merges the sub-goal's branch into the unit's instead: a clean merge ends the step as `moved`, and the flow runs the project's checks again on the two together, with no agent, before absorbing; a merge with conflicts is committed with its markers and ends as `conflict`, which the flow routes to the bead's builder, and from there the whole pipeline runs again. Code refuses to absorb while a conflicted file still holds a marker. Either way the unit's change is squashed onto the new tip, so the sub-goal's branch stays one commit for each bead, in a line. A builder is told its paths, and leaving them is recorded and reported to the foreman, not refused.
- **Sub-goals are worked on side by side unless one builds on another, and land one at a time.** A director with more than one slot may have that many sub-goals not yet landed, each with its own foreman. A sub-goal it opens names the sub-goals it comes *after*, and code refuses to open it while one of those has not landed. Nothing else keeps two apart: their paths may overlap, and a sub-goal may have none. A sub-goal's paths, when it has them, bind its foreman, whose beads keep inside them. Shipping is where sub-goals are folded together. A project ships one sub-goal at a time, across all its goals: one shipped while another is shipping waits in line, in the order asked for, and starts when that one has landed or parked. A ship pipeline begins with the `sync` action, which fetches and merges the default branch into the sub-goal's branch: `current` if there was nothing to take in, `moved` after a clean merge, `conflict` when a builder has to resolve it, and nothing is pushed while a file still holds a marker. Everything after it, the whole verification, the pull request and CI, therefore runs on the sub-goal together with what landed before it, and no CI run is spent on a base that is already stale.
- **A dependency keeps work apart, and a file two pieces both change does not.** Owner's decision, 2026-11-17, replacing the rule of 2026-11-16 that work ran side by side only on declared paths that did not overlap. That rule stood in for the thing it was for: not building on a dependency that is still being built. It was a poor stand-in both ways. On the Zig project it kept two goals waiting 28 hours behind one whose charter named no paths; of 700 pairs of beads only 13% went on to change a common file once shared files were left out; the 7 merges of a moved tip the records hold were all clean; and the one dependency in flight that day, a failure converter built on another bead's context type, was recorded nowhere but in the director's prose, and was kept in order only because the two beads' paths happened to overlap. So the dependency is now what is declared and checked: by the designer for beads, by the director for sub-goals, by the executive's judgment for goals. What two pieces of work both changed is merged where it always was, when the second bead is absorbed and when the second sub-goal ships. What the owner accepted with it: a conflict costs a bead its pipeline again, a dependency the designer leaves out costs the later bead its work, and a clean merge is seen together by the checks at once but by a reviewer only when the sub-goal ships. Where nobody has said what builds on what, a sub-goal with no design, the old rule stands, and there a goal definition's `shared_paths` (a README, a table of what is supported, changelog entries, a generated index) are still left out of the overlap check. Landing does not change: one pull request at a time, each sub-goal taking in the default branch first.
- **The tracker is the director's to keep.** Owner's decision, 2026-11-14: the director may write to the tracker itself (retitle, re-describe, link, file, defer), as the actor `factory-director`, and says what it changed in its summary. Starting, shipping and completing stay decisions that code checks and carries out, and a change to a bead's acceptance criteria stays an `edit` decision under the goal's permissions. This is a first step toward a director that manages more by itself. Since 2026-11-18 the factory also works on its own repository and ships what it lands (below).
- **A project can have an executive.** With an `[executive]` table in the project's file, the owner's top-level message in the channel goes to the project's *executive*, not straight to a director. It is a conversation in one session: the executive answers what it can from the repository, the tracker and the goals in flight, and when it knows what the owner wants it opens a goal under one of the project's goal definitions. The goal takes over the thread, and its director is briefed with the executive's handoff and what was said, then agrees the charter with the owner as before. A charter may now name the goal's *paths*; its sub-goals keep inside them. When no definition suits the work, the executive proposes one instead, a *definition proposal* (`propose_definition`: the TOML, a reason for the owner and the handoff), and opens nothing. Code checks the proposal with `check_candidate` within the same turn, and every problem goes back to the executive as any refused result does, so nothing that would fail `factory goal enable` is posted. One that passes is kept on the thread's record (its text, hash, reason, handoff, state and message) and posted in the thread with its full text, or for an ID in force a unified diff against that definition, and two buttons, `definition_approve` and `definition_reject` (`crates/factory-driver/src/goal/proposed.rs`). The owner's Approve does not wake the executive: it puts the definition in force with `enable_definition`, which checks the set again as it stands then and, with a problem, stores nothing and has the problems posted; it files the catch-up bead with `file_catch_up_bead`, and opens the goal in the same thread, pinned to the stored copy and handed the executive's handoff, as `open_goal` does, so the director's first turn in the thread follows at once. A proposal may have a `[schedule]`, and is checked the same way; it says so on the record (`schedule`, in words), in its message and on its Approve button, and its handoff may be empty. Approve on it stores it and files the catch-up bead the same way, but opens no goal, since the factory runs a scheduled definition by the clock: it has the running worker take it up with `tell_engine` (`factory-driver`), the code `factory goal enable` uses, which runs the engine's `enabled` command and so has the project told to look now; it logs what the engine said with `definition.approved`, and posts in the thread that the definition is in force, its hour and interval, and when it next runs. The thread stays the executive's: the owner's next reply there reaches it in the thread's session, told that the definition is in force. The owner's Reject stores nothing: it marks the proposal rejected and wakes the executive once in the thread's session (`front_turn`, its session resumed) with the rejected proposal named, and the owner's next reply in the thread goes to it as why, and is kept on the proposal. While a proposal waits, each reply of the owner's in the thread reaches the executive with that proposal named as still waiting, and a new proposal from it supersedes the one waiting, whose message then says so. A press on a proposal already approved, rejected or superseded does nothing but say so, so only one that waits is ever stored. A Reject that meets every account at its limit is on record at once, and when the press is handed in again the executive hears of it then.
- **Goals take turns unless the executive says they may run together.** A project runs so many goals at once: its executive's `slots`, or `max_goals` (one unless set) when it has none. A goal the owner starts beyond that is queued: no director runs and nothing starts, and when a running goal ends the one that has waited longest starts by itself. With an executive and room to spare, a goal started while another runs waits for the executive's word. It is woken, in a fresh session, with the running and the waiting goals, their plans and their paths, and names the ones to start: those that build on nothing a running goal has still to land. Code checks only the limit; paths that overlap, or a charter with none, keep no goal waiting. One left waiting starts when a running goal ends, and when nothing else is running no one is asked. What the owner writes to a queued goal is kept for its director. Across all of a project's goals sub-goals still ship one at a time, each taking in what landed before it.
- **Work in hand is kept on the remote.** With `sync_branches` in a project's record, the driver pushes a unit's branch to the remote whenever it has moved: after every step, and during an agent's run each time the agent commits, which the builder is told to do as it goes. When a bead is absorbed, the sub-goal's branch is pushed, and only once that has succeeded is the bead's own branch removed from the remote, since until then it is the only copy of that work off the machine. This is code in the driver, not a step a flow could leave out and not something an agent is trusted with. A push that fails is recorded and holds nothing up. Pushes respect the project's write list, as publishing does. Nothing restores from these branches: they are there for a person to recover from if the machine is lost. Shipping a sub-goal is unchanged, and finds its branch already on the remote.
- **Issues follow beads.** A project can keep GitHub issues in step with its beads (`issues = true`). The tracker holds each bead's issue link. A bead that has none gets an issue when the factory files it, and again as a backstop when its pipeline starts. A bead filed any other way, by the owner or another agent with `bd create`, is caught by the project's *issue sweep*: a Temporal Schedule (`issues-<project>`, every `issue_sync_secs` of the `[temporal]` table, an hour unless set) that the worker makes when it starts and makes again when it is not as this release would make it, and that starts one run at a time. Each run gives every open bead without an issue one, made as above, and brings every issue's type and priority into step. It leaves a bead filed less than ten minutes ago, and one the factory's own actor has claimed: whoever filed or claimed it is making its issue, and a second would be a duplicate. A run in which some bead could not be brought into step fails and names each; the next run tries again. Owner's decision, 2026-11-16. An issue carries the bead's type and priority twice: as labels, and in the repository's own issue type and priority field where the project names them (`issue_types`, `issue_priority`), which are what GitHub sorts and filters by. Those are found by name and set by ID, each whether or not the other can be, when the issue is created, each time work starts on the bead, and when the director changes the bead's priority; `factory issues sync <project>` does the same sweep at once. A failure to set them is recorded and holds nothing up. The publisher is told which issues its pull request closes, and code refuses a pull-request body that does not close each one with a closing word, so that GitHub closes them when the pull request merges. A sub-goal's pull request closes the issue of every bead it absorbed.
- **Findings are ruled on, not left.** When a pipeline ends, what its tester and reviewer left unfixed goes to whoever started it, the sub-goal's foreman or else the director, which files each as a bead or drops it with a reason.
- **What testers find is counted by class, and a class is closed by a check.** A tester gives each critical or major finding a `category`, a short key for the kind of mistake, and code refuses one without it. The classes are counted across the units of a project, and a builder's first brief lists the most frequent, so that a mistake that has broken earlier beads is looked for before the next one is handed over. That list is words, and words are the stopgap: a bead that a maintainer, a director or a foreman files may name the class its check closes (`closes_class`), when it builds a tool every later change runs. The factory keeps which bead answers each class (`projects/<id>/checks.json` under the state directory). While the bead is open the class is shown as having a check being built, and no second one takes its place. When the bead lands, code records how many beads the class had broken, and the class leaves the builder's brief: the check runs on the change, so nobody is asked to remember it. If the class breaks a bead after that, the check has let it through: builders are told again, the measures say how many got past, and a new bead may answer the class. Not yet proved by code: that a check does catch the cases of its class, which today rests on its bead's own tests, tester and reviewer. A tester's brief lists the same keys, to reuse. `factory findings <project>` prints the counts.
- **A command proves that new tests test the change.** A flow may run a project's *test proof* as a command step before the tester: each test the change adds or alters is run on the code as it was at the unit's base, where it has to fail. One that passes there goes back to the builder. One that cannot be compiled or reached there is weaker proof, and the tester and the reviewer are told which those are. The reviewer is no longer asked what this settles; it judges correctness by reading, idiom and quality against the project's written `standards`, scope, and the tester's open findings. How a change is split into its tests is the project's tool: Zig keeps tests beside the code, so its tool splits at `test` blocks.
- **A goal's stop condition can be a command.** A goal definition may name a `stop_check`, a command of the project. Code runs it on the default branch whenever that has moved, shows the director what it said, and refuses the director's proposal that the goal is complete while it fails. It is how a goal is measured against something its own builders do not write.
- **A sub-goal is designed before it is built.** When the goal definition has a `[designer]` table, opening a sub-goal runs its *designer* first: one agent that reads the code and the sub-goal's beads and returns the public interface, the errors and invariants, where the code goes, the order of the beads and what each comes after, or says that the sub-goal is split wrongly. The director accepts the design or sends it back with a note, up to three times; then it must accept or ask the owner, and the owner's reply in the goal's thread allows three more (the rounds keep their numbers). Until it accepts, the sub-goal's foreman is not woken and code refuses any start or ship in it. The accepted design is in the first brief of every agent of every pipeline of the sub-goal, and of its foreman. The designer runs as a turn of the project's tiers, so while it reads no other tier of that project is woken; pipelines carry on. Not yet done: stopping a ship whose public interface goes beyond the design, which needs a list of the project's exported names that the project does not produce yet.
- **A goal definition can be put in force without a release.** Beside the release's `goals/<project>/<id>.toml`, the factory keeps a store under its state directory: `goals/<project>/<id>/<hash>.toml`, each copy (a *stored definition*) named by the SHA-256 of its text, and a `current` file naming the copy in force for that ID. Every read of a stored copy checks its text against its name, and refuses one that no longer matches: a copy changes only by storing another. A stored copy in force takes the place of the release's definition with the same ID, and is checked as a release file is. When a release's text for that ID is the stored copy's, the release has caught up: the `current` file is removed as the definitions are read, and the release's file is in force again from then on. While they differ the stored copy still wins, and `factory goal check` prints a warning naming both. Earlier copies are kept, so a copy can be read back by its hash whether or not it is in force (`factory-config`, `ConfigDir::store_goal_definition` and `stored_goal_definition`). One check runs over the set in force, the release's definitions with the stored copies in their places: `factory goal check`, `factory-engine check`, which deploy runs before it makes a release current, and the factory's own load all use `check_definitions` (`factory-driver`), so a release under which a stored copy names what it lacks, such as a pipeline, is refused. A definition is put in force through `enable_definition`, which first checks the project's set as it would be with the candidate stored (`check_candidate`), stores nothing when that finds a problem, and returns each problem as a line. The owner does it with `factory goal enable <project> <file>`: it prints each problem and stores nothing, or stores the definition, tells the running worker through the engine's command below, and files a *catch-up bead* to commit the file as `config/goals/<project>/<id>.toml`, with its text and hash, so that a release catches up and the stored copy is dropped. Goal definitions are the factory's config, so that bead goes to the factory's own project (the one with `[self_deploy]`) whatever project the definition is for (`file_catch_up_bead` in `factory-driver`); where that project forbids its steps the path, as it does its own definitions, the bead says the owner commits it and is filed deferred. A text the release's file already has needs no bead. A worker that could not be told, or a bead that could not be filed, fails the command after the definition is in force, and says which. `factory goal list` shows every definition in force, and whether its text is the release's or a stored copy. The running worker takes a definition put in force up without a restart: `factory-engine enabled <project> <definition>` (`tiers::take_up`) starts the project's workflow if it is not there, since a worker starts the workflows only of projects that have definitions, and tells a project whose new definition has a schedule to look now, since its workflow learns when it is next due only from a turn. A workflow that is running reads the definitions in force at each turn. The listener learns the channel of a project that had no definitions when the intake next starts it afresh. The store's project directories sit beside the goals' own records, which are named `<project>-g<n>` and hold a `goal.json`; a reader of goal records passes over a directory without one. A goal is pinned to the definition it opened under: when it opens, the text in force for its definition, the release's or a stored copy, is kept in the store under its hash (`ConfigDir::pin_goal_definition`), without changing which copy is in force, and the goal's record holds the hash (`definition_hash`). Every wake of the goal, and every check of what its tiers decide, reads that copy, so a definition put in force or a release whose file differs after the goal opened does not change it. A goal record written before goals were pinned has no hash, and reads the definition in force.
- **A definition can run by itself, and what it finds it may have built.** A goal definition with a `[schedule]` table is not a goal the owner opens: the factory runs it at its hour, every so many days, and a time the worker was away for is made up once. Each run is one agent, the *maintainer*, with a fresh session. Code gives it the charter, the *measures* it computed from the units' records since the last run (classes of defect that have broken three beads or more, checks that failed and then passed on one commit, pull requests whose CI went red, beads that took three rounds of fixing, pipelines that parked, fixes that removed tests), the files that grew most on the default branch, what the default branch's own CI says of the newest commit it ran on, the output of each command of the project the schedule names in `reports` (for what the factory's records cannot show, such as duplicated code), the open work, and the journal the last run left. It may file beads, up to the definition's limit; code refuses a result that starts, continues, ships, closes or edits anything. What it found is posted in the project's channel. A run is a turn of the project's tiers, so no engine workflow knows of schedules: the project's workflow is told when the next run is due the same way it is told of any agent to try again.
- **What a scheduled run marks, the factory builds, and what keeps breaking calls a run.** Owner's decision, 2026-11-16: the loop from what testers find to the check that stops it closes without the owner in it, and what can be a tool is not left as prose. A schedule may name the definition its beads are built under (`build_under`). A run then marks beads to build, ones it files or ones an earlier run filed that nothing has built, with a plan and the paths the work will change. Code opens a *maintenance goal* for them under that definition: it writes the charter from the run's result, starts the goal as the owner's Start would, in line behind the project's running goals or beside them on paths that do not overlap, and the goal takes the thread of the run's message in the channel. From there it is a goal like any other: director, designer, foreman, pipelines, one pull request, CI. Its stop condition is one code decides: when every bead it was opened for is closed, the goal is complete with no agent run and no Accept. A schedule has one such goal at a time; while it builds, a run may file and may not have more built. A schedule may also say how many beads a *finding class* has to break before it calls a run (`when_class_breaks`): code counts the beads each class has broken from the units' records, keeps what each run was shown, and makes a run due at once when a class has broken that many more. No model is asked whether it is time. The maintainer is told to build tools that every later change runs (a lint rule, a check in the build, a test helper) behind a command the project's flow already has, and to keep a rule in the project's written standards for what no tool can see.
- **The factory is reviewed every night, and only the owner's button acts on it.** A schedule with `proposes` is a *review*: its agent, the *inspector*, is not shown one project's code but how the factory as a whole ran since its last run, as `factory report` builds it from the records, with what became of every *proposal* it made before. It returns goals, at most `proposes` of them, each for a project the factory knows, with an objective, a stop condition and the figures that call for it; code refuses beads, starts and anything else. Each is posted in the review's channel with an approve and a decline button and kept in the schedule's record as waiting. Approving one for a project that has a goal definition the owner can open puts it to that project as the owner's own message in its channel would be: to its executive, or to a new goal's director for a charter. For a project that is another's turn to write, the turn leaves the event in `handed` and the engine signals it to that project's workflow, or keeps it as an owner's message that could not be delivered. Approving one for a project with no such definition files it as a bead in that project's tracker. Declining records it, and the owner's first reply under the message is kept as the reason. A press on a proposal already answered does nothing. A proposal for the factory itself that the owner approves opens a goal under the `software-factory` project's `build` definition.
- **The factory works on its own code every night, and ships what it lands.** Owner's decision, 2026-11-18, replacing the rule of 2026-11-16 that the factory does not ship itself. The `software-factory` project's `nightly` definition is a *direct* schedule (`direct = true`, with `build_under`): no maintainer decides what to build and no director starts or watches the work. At its hour, while no earlier run's goal is open and the project has a place for a goal, code files one bead whose description is the schedule's charter, opens a goal for it under `build_under` and starts the bead's pipeline itself (`run_direct` in `factory-driver/src/goal.rs`). The pipeline, `factory-self`, is one Opus builder session that reads the charter, decides what most needs doing and does it; then `cargo xtask check`, the publisher in the same session, the pull request, CI, a squash merge, and the `deploy` action. There is no tester and no reviewer. When the pipeline ends, code settles the goal with no director (`settle_direct`): a landed bead completes it, a builder that found nothing to do (`already_done`) closes the bead and completes it, and a pipeline that parked or failed stops the goal and is put to the owner, with its unit kept to continue by hand. What keeps the run in bounds is code and the owner's files: the project forbids changes to `.github`, its own record, its flow and its goal definitions, so an agent cannot loosen the limits it runs under, and the CI job that every change must pass is one of those files. The charter tells it not to weaken a check, a test, a gate or the code that limits agents, and nothing but that sentence and the checks themselves enforces it.
- **Nothing ships while the default branch is red.** No pipeline looks at the default branch's own CI once a pull request has landed. For a goal that ships sub-goals, code reads it each time the director is woken: the workflow runs on the newest commit that has any. While one has failed, the director's brief says so, the owner is told once for that commit in the project's channel, and code refuses `ship`, since every sub-goal that ships takes the failure in and each would try to mend it in its own pull request. One ship is let through: a sub-goal the director says is the fix, with what broke and how it is mended, which its pull request's own checks have to bear out before it lands. A CI that is pending, unreadable or only cancelled refuses nothing.
- **Ending is the owner's act.** The director proposes completion with evidence; the factory posts it with an Accept button. Accept marks the goal complete with no agent involved. A reply instead is guidance, and the goal goes on.

What runs on this machine is one process, the engine's *worker*. Everything that waits, wakes, retries or remembers what is still to be done is a workflow on the Temporal server the `[temporal]` table names, and the worker does their work: the steps of pipelines, the turns of the tiers, the check of the accounts, the socket to Slack. The factory listens to Slack over that socket (Socket Mode), so nothing is polled and nothing needs to be reachable from outside. A worker that dies loses nothing but the time of what it was in the middle of: an agent step is given to the worker that starts next, which resumes the run's session; a turn or a command step is done again; and what the owner wrote meanwhile is in a workflow or, for the moment the socket was down, kept in a file and handed on. A worker that is alive, and from which the server has merely not heard (the network between them was down for a minute), is given the same step again while its first run of it is still going. That attempt joins the run in flight and is handed what it comes to (`Flights` in `factory-engine/src/steps.rs`): a step never has two runs at once on one unit, whose record and worktree one run at a time writes. A step that ended, and whose result the server never took (its worker was stopped in between, or its heartbeat ran out over a long drain), is given out again too. That attempt finds the step's end, for the same round, last in the unit's log and hands back the outcome recorded there, with a `step.recalled` event, instead of running the step a second time (`Driver::run_step_at` in `factory-driver/src/lib.rs`); the unit's record is written before that end is logged, so it holds everything the step did. Anything logged after the end, such as a park or the unit being taken up, means the step is new work and runs. A worker asked to stop at a safe point goes on heartbeating the steps it is in the middle of until they end, so a step in flight over a drain ends on that worker as its first attempt; a test drains a worker under an agent step that runs several heartbeat timeouts past the drain.

| Workflow | ID | What it is |
|---|---|---|
| Pipeline | `pipeline-<goal>-<bead>-…` | One unit's walk through its flow, a step at a time |
| Project | `project-<id>` | A project's tiers: takes everything that happens to the project, one thing at a time, each as a *turn* |
| Intake | `intake` | Keeps the listener on Slack and the watcher of pipelines alive |
| Accounts | `accounts` | Says which account each agent step runs under |
| Issue sweep | `issues-<project>-<time>` | One sweep of a project's open beads against their GitHub issues, started by the schedule `issues-<project>` |

`factory-engine project <id>` shows where a project's tiers stand, `factory-engine standing <pipeline>` a pipeline, and `factory-engine accounts` the accounts; the server's own pages show the same, since everything a workflow starts says what it is for.

launchd keeps the worker running (`factory service install`): as an agent of the desktop session of the user the factory runs as, because that session is where the login Keychain is unlocked, and limited to that session so that a copy can never run without it. It starts at login and again whenever it exits. launchd gives a job almost no environment, so the job is started through the user's login shell, and the worker and every agent and command it starts have the `PATH` and the rest of what the shell's profile sets up, as the user's own terminal does. What it runs is a *release*: one build of the factory and of the engine beside a copy of the config that build reads, in a directory of its own. A link names the current release and a deploy replaces the link in one step, so a build never reads a config written for another; a running worker goes on with the release it started from. Before the link moves, the release's own engine is asked whether it can read the release's config (`factory-engine check`), and a release it cannot is removed and refused: an engine built before the config's newest fields, as when only the factory's binary was rebuilt, otherwise leaves the service starting and dying (owner's decision, 2026-11-18, after a deploy did that for a minute and a half). The job starts `factory serve` from the current release, which puts that release's engine at `bin/factory-engine` under the state directory and becomes its worker. The engine runs from there, not from the release, because this machine allows a program to reach the server on the local network by its path. With `signing_identity` in the `[service]` table, a release's `factory` and `factory-engine` are signed with that code-signing identity from the owner's login Keychain, under names that never change (`software-factory.factory`, `software-factory.factory-engine`), and the signature is verified before the link moves; a release that could not be signed is removed and refused, as one whose engine cannot read its config is (`sign_program` in `factory-driver/src/service.rs`). macOS keeps what it allowed a program, Full Disk Access and reaching the local network among it, for the program's signature. A program with only the linker's ad-hoc signature is known by the hash of its build, so every deploy installed a program macOS had never seen and lost what the one before was allowed; signed this way every build is the same program to it. The identity's key must let `codesign` use it without asking, since the factory deploys its own landed commits with nobody at the screen. Owner's decision, 2026-11-20, after a deploy lost Full Disk Access again.

The factory's own project deploys itself (`[self_deploy]` in its record): its flow ends with the `deploy` action, which no other project may name. It checks out the commit that landed in a worktree of its own under the state directory (`self-deploy/<project>`, kept between deploys so the build starts from what the last one left), builds it with the project's `release` command, installs the factory's binary with the config at that commit as a new release (the engine's check of the config included) and makes it current, and then sets the drain flag. It never waits for the restart, since the service it would wait on is the one running it. A build that fails, or leaves no program, changes nothing and parks the unit. `factory service rollback` makes the release before the current one current again, keeps the one it replaced, and restarts the service onto it.

A restart is a request, not a kill (`factory service restart`, or `deploy`, which makes a release first). The worker takes on nothing new, finishes the steps and turns it is in the middle of, and ends; what it did not take on waits on the server. launchd starts the current release, and its worker goes on with all of it. `--now` stops it where it stands instead: the steps and turns that were cut off are done again, an agent's in the session it had. For the case nobody asked for, a crash, the worker notes every long run it starts with the process's ID and start time, and a worker that starts kills whatever an earlier one left running before those steps are done again. A project's tiers take their turns one at a time, so two goals of a project take turns thinking, and a goal's cap above one waits on conflict handling.

Without `tiers = true` in the `[temporal]` table the same supervisor runs as a loop inside `factory serve`, with pipelines on its threads or, with `pipelines = true`, on the engine. That is how the tests of the driver run it, and what a factory without a Temporal server has.

## Watching the factory

`factory-dash` serves the owner's workspace (its design and the reasons for it are in [dashboard.md](dashboard.md)). A sidebar lists the places: the *inbox*, the floor and each project, each project with a mark for whether it is working, has something parked or is waiting on the owner. The floor shows the agents running now and each account's windows with how fast they are being used and what is running on it. A project is drawn as a graph (Svelte Flow), top down: its executive, goals, sub-goals and beads, a bead that is running, parked or asking the owner drawn as its whole pipeline, every step and route of its flow with how often the bead took each route and the step it stands at. The executive, a goal and a sub-goal open the same way into their agents at work: what woke them, each agent's runs, and what each decided, counted from the tier's log. Every card opens and folds. The owner can drag anything on it, which that browser remembers, and Tidy lays it out again. Any agent's run can be opened and read as it is written, and so can the runs before it, and a goal's or an executive's conversation with the owner is read back from the records.

The inbox holds everything the factory has stopped to ask the owner: a charter to start, a completion to accept, bead changes to approve, a director's question, an intake waiting for the owner's reply, a review's proposal, a goal definition the executive proposed, a pipeline step's question, and a pipeline run by hand that parked. A proposed definition is read from the executive's record (`executive.json`, each thread's `proposals`) while its state is `waiting`, and shows the reason, the text or its diff against the definition in force as the Slack message has it, and the two buttons with the value Slack's carry (`<thread>/<n>`). Each is worked out from the records on every look (`crates/factory-dash/src/inbox.rs`), so it leaves the inbox when the factory has taken the answer in, wherever the answer was given.

It is observability and not a part of the factory. The crate uses no factory crate, and the factory knows nothing of it. Everything on the page is read from the records the factory already keeps under its state directory: the executives' and goals' records and logs, the schedules' records, each unit's record, flow and event log, the log of every run, and the accounts' windows. The server reads the records every two seconds, only while somebody is looking, and streams the picture to the page (`/api/stream`, server-sent events): the whole of it once, then only the parts that changed, when they change, which the page applies where they are so that nothing the owner is reading, typing or dragging is drawn again. An account's rates are worked out to the minute, so the clock moving alone does not change the picture. A record that is missing or has changed its shape leaves a gap on the page, not an error; `crates/factory-dash/tests/serve.rs` holds the shapes it relies on, so a change to one of them is a failing test there. The rate an account is used at is worked out from what the runs that ended said of its windows, so the dashboard keeps no history of its own.

The owner may answer from the page (owner's decision, 2026-11-18, as a step toward leaving Slack). The dashboard still writes nothing and opens no connection of its own: an answer is handed to the factory's engine command, `factory-engine owner <project> press <button> <value>`, `factory-engine owner <project> say <channel> <thread> <text>` or, for a new message as at the top of the project's channel, `factory-engine owner <project> new <text>`, which signals it to the project's workflow as the same event a press or a reply in Slack is (`Event::Slack`), from the first owner the Slack settings name (`owner_press` builds the press). The tiers therefore cannot tell the two apart, and a stale press is ignored as a stale button in Slack is. A reply is also posted in the Slack thread it answers, and a new message at the top of the channel, marked as from the dashboard, so Slack still reads whole. The only program the dashboard starts is that command, from the current release with that release's config unless told otherwise, with each argument checked (a button the factory posts, a name of the factory's or a proposed definition's `<thread>/<n>`, a thread's time stamp, a reply of at most 8,000 characters after a `--`), never through a shell and one act at a time; a test fails if its sources gain any other way to start a program, write, or connect. A question a pipeline's step asks is still answered in Slack, since its driver reads the reply from the unit's thread there.

Who may read it is set where it is started. `--allow <network>` names a network that may connect, and may be given more than once; with none, only the machine itself may. A connection from any other address is closed before a byte of it is read. The page is served only under an address or a name given with `--name`, which stops a page on another site, open in a browser on an allowed network, from reading it under a name of its own. Who may act is narrower: `--act-allow <network>`, this machine alone unless given, and `--read-only` offers no acts at all. An act is a `POST` to `/api/act` with a header and a JSON type that a browser sends only from the page itself, and from a page whose origin is the page's own; every other request is `GET` or `HEAD`. A run's log and a conversation are found only by the plain names the factory gives units, goals and logs, and the page loads nothing but its own files. What an agent's tools printed is shown as it is, with anything that looks like a token taken out.

The page is a Svelte app in `crates/factory-dash/web`, built into `crates/factory-dash/assets` and embedded in the program, so building the program needs no Node. The built files are kept in the repository; a change to the page is a change to `web/src` and a rebuild (`npm ci && npm run build` in `web`).

It runs as a launchd agent of its own, `software-factory-dash`, from a copy of the program outside the releases, so a deploy of the factory neither stops nor changes it:

```bash
cargo build --release --locked --offline -p factory-dash
factory-dash serve --listen 0.0.0.0:8717 --allow 192.168.101.0/24 --act-allow 192.168.101.0/24 \
  --temporal-ui http://<server>:8080 --slack https://<workspace>.slack.com
factory-dash snapshot    # the same picture once, as JSON
```

## Failure classes

Every failure the factory must survive is listed in a catalogue with how code detects it, its class, the response and the resume condition. There are three classes.

- **Unit**: one unit is affected. It is retried, sent back a step, or parked. Everything else carries on.
- **Factory-wide**: nothing can usefully be dispatched (both accounts limited, Redis down, GitHub down). The driver pauses, keeps observing and resumes by itself.
- **Needs-owner**: only the owner can fix it. The scope it affects is paused and the owner is told once.

## Proof

A milestone is proved by its *gate* and by nothing else: `cargo xtask gate <id>` runs the checks in `gates/<id>.toml` and exits 0 only if every one passed. Each acceptance line of a bead is a check in its epic's gate. Checks have one of four tiers.

- **hermetic**: no network and no model. Runs anywhere.
- **host**: needs this Mac's real services, launchd jobs or worker slots.
- **live**: makes real Claude calls, on Haiku.
- **owner**: needs something only the owner can supply.

A skipped tier makes a gate incomplete, and an incomplete gate cannot close a milestone.

## Build order

Deterministic tools first (foundations, host proofs, state, supervision, the Claude adapter, work sources, GitHub, checks, Slack, tasks, operations), then the driver that composes them, then the parts where a model's behaviour matters (briefings and prompts, end-to-end runs, agent tasks, the first real project). `bd ready` gives the next bead.
