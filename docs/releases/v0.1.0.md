## Highlights

The first release of the software factory, and an **experimental** one: the
configuration format, the records under the state directory and the commands
may all change in later 0.x releases without a migration path. The service
(`factory serve` under launchd) runs on macOS; the programs are built for
Linux too, where everything except the launchd service runs. It needs a
Temporal server, the Claude Code CLI, `gh`, and `bd` with a Dolt server for
each project's beads.

### Added

- `factory run <project> <bead>` walks one bead through its project's flow, a
  TOML definition of agent and command steps under `config/flows`, to a pull
  request: build, check, adversarial testing, review, publish, and landing once
  CI is green, with no model in the landing path.
- Goals: a message in a project's Slack channel opens a goal, its director
  agrees a charter with the owner, and once the owner presses Start the goal
  runs on events. Goals work in sub-goals that each land as one pull request,
  with a foreman that builds a sub-goal's beads side by side and a designer
  that fixes a sub-goal's interface before any bead of it is built.
- A project executive sits between the owner and the project's goals: it
  answers the channel, opens goals, decides which run together, and closes
  beads that need no work.
- Projects can set `director_decides = true`, or a goal definition can override
  it, to have directors go with their own recommendations instead of waiting
  for the owner, and to end a goal once its stop condition is checked.
- Goal definitions take a `stop_check`: a project command the factory runs on
  the default branch, which must pass before a goal can be proposed or closed
  as complete.
- Scheduled definitions run by the clock: a maintainer files and marks beads
  to build, a daily review proposes goals to the owner, and an hourly issue
  sweep gives every open bead its GitHub issue with the issue's own type and
  priority.
- Everything runs on Temporal: one engine workflow runs any flow, each
  project's tiers run as a `project-<id>` workflow, and an `accounts` workflow
  hands each agent step a Claude account, picked by the usage windows of each
  account and waiting when all of them are at a limit.
- `factory service install` and `factory service deploy` keep the service
  running under launchd from a versioned release directory; a restart stops at
  a safe point and a crashed worker's leftover runs are cleaned up.
- `factory-dash`, a live read-only dashboard of units, goals, pipelines and
  accounts, served only to the networks given with `--allow`. Account cards
  show the 5-hour and 7-day windows across all models and each model's own
  weekly window, such as Fable's.
- A failed check is triaged before a builder is sent: rerun once, run on the
  unit's base to see whether the failure is the change's, and parked when the
  same failure comes back.
- Tester findings carry a class, and builders are told which classes recur.
- `factory report --since <period>` summarises units, cost, rounds, parks and
  waits from the factory's own records.
- `factory --version`, `factory-engine --version` and `factory-dash --version`
  print the release they were built as.
- Releases: `cargo xtask release-notes`, `cargo xtask package` and
  `cargo xtask release` cut a tagged release, and a workflow publishes archives
  for macOS and Linux on arm64 and amd64 with a `checksums.txt`.
